# Сравнение официального драйвера ASUS и Sweet

12 ноября 2026. **Переносимого исправления первичного NV timeout в проверенных функциях не найдено.** Новых изменений на планшет в этом раунде не устанавливалось. Выполнено сравнение исходников, проверены детали официального boot и повторно проверено рабочее соединение.

## Источники и существенное уточнение

Официальный архив ASUS `kernel_10_10_3_41.zip`, SHA-256 `81de9180c2426285a15fe721b4d7cc1baab49a492112299b89f85dc0434e6bce`, содержит tar.gz и **две** копии Prima:

- `kernel/drivers/net/wireless/prima`;
- `kernel/drivers/staging/prima`.

Раннее сравнение локального `stock-source/wlan_qct_wdi.c` использовало staging-копию. Она старее net/wireless-копии в том же архиве. Поэтому различие со staging само по себе нельзя считать изменением относительно реально выпущенной ASUS ROM. В этом раунде обе копии извлечены отдельно, без перезаписи друг друга.

Справочный Sweet — [Den147/Sweet_kernel_rebase, commit c1ec835b37a8ef39232cee7c4199d3b6b7196148](https://github.com/Den147/Sweet_kernel_rebase/tree/c1ec835b37a8ef39232cee7c4199d3b6b7196148). Это источник для сравнения; полное соответствие всей сборки установленному ядру не заявляется. Для ключевых параметров использовано и дизассемблирование точного установленного образа из предыдущего раунда.

## Что совпадает

Сравнивались токены тел функций с удалением комментариев/пробелов и нормализацией `__FUNCTION__` в `__func__`. Макросы, типы и preprocessing не вычислялись: равенство токенов не является доказательством равенства скомпилированных программ.

| Участок | ASUS net/wireless против справочного Sweet |
|---|---|
| `WDI_SendNvBlobReq` | Токены совпадают |
| `WDI_ProcessNvDownloadReq` | Токены совпадают |
| `WDI_ProcessNvDownloadRsp` | Токены совпадают |
| `WDI_GetMessageBuffer`, `WDI_SendMsg` | Токены совпадают |
| Семь проверенных CTS-функций: open/close, отправка, read/write/data callbacks, notify | Токены совпадают |
| `wpalDeviceInit`, `wpalDeviceClose` | Токены совпадают |
| Полный `arch/arm/mach-msm/smd.c` | Совпадает побайтово, SHA-256 `2d58284ef253736224d665c86818939e688e35d99d4d85faad327fc15b984464` |

Результаты для обеих ASUS-копий и хеши файлов: [машиночитаемое сравнение](../evidence/wifi-source-comparison-2026-11-12.json). [Скрипт воспроизведения](../experiments/wifi-source-comparison/README.md) проверяет наличие всех 15 выбранных определений, а не сравнивает пустые выборки.

В старой staging-копии CTS при постановке в очередь возвращает SUCCESS; в net/wireless и Sweet — E_RESOURCES, который WDI также считает успешной передачей с диагностикой. В полном неудачном NV-обмене нет сообщений CTS deferred queue / FIFO space not available. Кроме того, данные уже видны в исходящем FIFO. Это не даёт основания объявить старую семантику очереди ремонтом наблюдённого сбоя.

Отличие `WDI_ResponseTimerCB` от ASUS net/wireless: Sweet проверяет `bEnableSSR` и при выключенном SSR сообщает device error и возвращается. Это путь **после** таймаута; он не объясняет прекращение приёма девятого фрагмента. Включение SSR наугад меняет восстановление после ошибки, но не устраняет её причину.

## Проверка официального образа

Локальный официальный `boot.img`, SHA-256 `6e3583a2fbfc41c1ac058e12705db262939f72f77e589eafb59caea9ca1a7f44`, содержит Linux `3.4.0-g495a631-00001-g7bf065c`, сборка 7 февраля 2014. Ядро распаковано на ПК; встроенная конфигурация IKCONFIG прочитана без запуска этого образа на планшете.

И официальный boot, и установленный watchdog-кандидат используют `CONFIG_MSM_SMD_PKG4=y`. В официальном включён SMD logging, в нашем выключен. Это различие диагностической сборки, не доказанный дефект передачи.

Из официального ядра декодирована встроенная таблица kallsyms: проверены 96678 адресов/имён, маркеры и 256 token-index offsets. По её символам найдены фактические функции:

- `WDI_SendNvBlobReq` по `0xc0512030`: размер полного фрагмента `0xc00`, то есть 3072 байта.
- `WDI_SendMsg` по `0xc050e060`: SUCCESS и E_RESOURCES принимаются, как в net/wireless-копии; `wpalTimerStart` получает `0x2710`, то есть 10000 мс.
- `WCTS_SendMessage` по `0xc052030c`, `smd_packet_write` по `0xc002fb30`: доступны для дальнейшего точного сравнения. Побайтового равенства их с нашим бинарным кодом не заявляется: компилятор, адреса и окружение различаются.

Полные образы, распакованные ядра, таблица символов и дизассемблирование сохранены приватно на ПК. Официальный boot не прошивался: он не является заменой ядра Android 10.

## Отличие запуска WCNSS

В Sweet WCNSS core умеет отдельно загружать NV через канал WCNSS_CTRL для firmware версии >=1.4 по используемой проверке major/minor. В старом официальном core этого кода нет. На планшете версия читается как `01040102`, в журнале WLAN — 1.4.1.2.

В уже сохранённой полной трассе core загружает 29772 байта и получает `WCNSS_NVBIN_DNLD_RSP` в 12:51:30.187. Затем первая инициализация WLAN успешно завершается. Неудачный повторный обмен начинается только в 12:54:07.947. Двух одновременных загрузок в этом журнале нет. Второй канал — реальное архитектурное отличие, но отключать его на основании одного наличия нельзя.

## Состояние и следующий диагностический рубеж

Установленным остаётся boot `d2cacd5c413e13a17489b7161062f2e9edbe53c3044c33368380d66df80b8cfc` с рабочим watchdog completion repair. Новых тестовых служб, приложений, конфигураций или патчей в этом раунде нет. Финальная read-only проверка: Wi-Fi VALIDATED, crash buffer пуст, USB stay-awake=0.

Следующий полезный эксперимент должен различить **остановку всего удалённого WCNSS** и **остановку только обработчика WLAN_CTRL**. Для этого нужен узкий диагностический запрос версии по уже открытому WCNSS_CTRL во время зависания NV с одновременным снимком каналов и счётчиков. Обычное чтение sysfs `wcnss_version` возвращает кеш и таким тестом не является. Самостоятельно открывать уже занятый канал или писать в его FIFO из userspace нельзя считать безопасной заменой правильному запросу драйвера.

Пока такой диагностический инструмент не подготовлен и не проверен, новая функциональная правка не обоснована. Увеличение таймаута, замена одинаковых функций и автоматический бесконечный retry не представлены как устранение причины.
