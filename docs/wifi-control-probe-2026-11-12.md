# Диагностический запрос WCNSS: инструмент работает, таймаут не воспроизведён

12 ноября 2026. Подготовлен и установлен временный диагностический kernel. **Контрольный запрос версии к исправному чипу получил ответ. В четырёх последующих переключениях исходный NV timeout не возник, поэтому состояние чипа именно при зависании пока не определено.** Успешные переключения не объявляются ремонтом.

## Что проверяет инструмент

После настоящего WDI NV timeout, перед обычной обработкой ошибки, ядро один раз отправляет восьмибайтовый запрос версии через уже открытый WCNSS_CTRL. Это отдельный канал от зависающего WLAN_CTRL. После успешной записи допускается однократное ожидание 250 мс; исходный таймаут NV 10 секунд не увеличен.

Обычный обработчик ответа на версию автоматически запускает загрузку NV в WCNSS core. Для диагностического ответа этот побочный эффект подавлен; начальная загрузка NV и нормальные ответы сохраняют прежний путь. Контрольный запуск запроса при здоровом Wi-Fi доступен через временно изменённое чтение sysfs `wcnss_version`. Один запрос на загрузку суммарно для обоих способов запуска.

Ответ доказывает работоспособность этого служебного запроса, но не всех служб или ядер WCNSS. Отсутствие ответа за 250 мс само по себе не доказывает полный отказ чипа: нужно учитывать поздний ответ, состояние транспорта и момент восстановления.

[Фактический ARM-код, linker script, host test и технические ограничения](../experiments/wifi-control-probe/README.md). 368 байт кода/констант размещены в проверенном нулевом промежутке выравнивания text перед rodata; размер ядра, ramdisk и расположение частей boot сохранены. Рабочая watchdog completion repair включена. Флаг эксперимента использует неиспользуемый хвост буфера версии только в этой точной бинарной сборке и исчезает при перезагрузке. Это диагностический прототип, не рабочий пакет исправлений.

## Проверки и результаты

97 host-сценариев проверили регистры/стек, байты запроса, one-shot, NULL/неинициализированное состояние, ошибки записи, отсутствие места в FIFO, обход повторного NV и возврат к исходному sysfs-коду. Внешние функции и приход ответа моделировались; отдельный повтор публичного host test воспроизвёл результат.

Через TWRP записан только boot `/dev/block/mmcblk0p14`, 16 MiB. Резервная копия рабочего boot проверена на ПК до записи, а записанный образ — полным readback. До первой записи один пустой USB-ответ остановил процедуру; на первой попытке отката пропадание USB также остановило процедуру до записи. Повторные проверки выполнялись заново с теми же ограничениями по разделу и хешам.

Диагностический boot SHA-256: `fadd831c1e5caa8153107441250ddff5b94eeec61eaa14741c4a24cffb95d1cd`.

| Этап | Наблюдение |
|---|---|
| Исправный чип после первой загрузки | `tx=8 state=2`: запрос принят, реальный ответ версии 01040102 получен за отведённое окно. После ответа повторная загрузка NV не наблюдалась. Crash buffer пуст. |
| Перезагрузка для сброса one-shot | Диагностический флаг очищен; старый контрольный запрос не мешал следующему тесту. |
| Три переключения без подробной CTL/PAL-трассы | NV timeout и автоматический probe не возникли. Окна наблюдения около 37 с каждое. Boot и system_server не перезапускались, crash buffer пуст. |
| Ещё одно переключение с CTL/PAL-трассой | 10 NV-запросов / 10 ответов, таймаута нет. Подтверждённый интернет через 24,94 с, повторное включение не потребовалось. |

Подробная трасса включалась только для последнего цикла. Активный персонализированный INI восстановлен побайтово, вместе с владельцем, правами, label и mtime. Собственный logcat-сборщик остановлен, временный каталог удалён; перезагрузка в recovery сбрасывает runtime trace masks. USB stay-awake возвращён в исходное 0. Пользовательские MAC, полные образы, конфигурации и сырые логи остаются на ПК.

## Вывод и применение в дальнейшем

Диагностический boot удалён через TWRP. [Проверка полного readback при откате](../evidence/wifi-control-probe-rollback-2026-11-12.json) подтвердила рабочий SHA-256 `d2cacd5c413e13a17489b7161062f2e9edbe53c3044c33368380d66df80b8cfc`; тот же хеш прочитан после загрузки Android. Активный INI совпал с сохранённым оригиналом, `/data/local/tmp` пуст, crash buffer пуст. Location=3, Bluetooth=0, USB stay-awake=0. Wi-Fi после последней загрузки ожидает подключения к сети для заключительной проверки интернета.

Инструмент пригоден для следующего воспроизведения сбоя: здоровый контроль уже исключил простую ошибку формата запроса или неработающий RX gate. Однако автоматический hook на настоящем NV timeout физически в этом раунде не сработал: проверены только его модель и общий код запроса через контрольный вход. Нельзя делать вывод, какая часть чипа зависает, или считать сам диагностический образ исправлением.

Для повторения нужен тот же точный boot и контролируемый тест с журналом, затем возврат рабочего boot. На Android 13, другом ядре или другом планшете адреса и структура данных неприменимы. Оставлять этот вариант для обычной эксплуатации не требуется.
