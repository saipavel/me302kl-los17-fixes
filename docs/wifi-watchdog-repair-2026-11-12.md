# Установлена правка завершения watchdog Wi-Fi: 12 ноября 2026

**Правка установлена через TWRP и проверена на настоящем таймауте чипа.** После неудачного восстановления служба больше не осталась ждать завершения уже вышедшего потока; повторное включение восстановило интернет без перезапуска Android. Первичный NV-download timeout и поиск сети с погашенным экраном этой правкой не исправлены.

## Изменение и проверки перед установкой

В `VosWDThread` обычный выход уведомляет ожидающий код через `complete_and_exit(&pWdContext->WdShutdown, 0)`. Выход после ошибки восстановления раньше просто возвращал 0. Затем `vos_watchdog_close` мог бесконечно ждать уведомления, которого уже некому отправить.

Теперь используется существующий правильный completion/exit. Пять изменений регистров переносят диагностическую строку из R4 в R6, сохраняя указатель контекста в R4; шестое направляет только reset-error exit к нормальному завершению. Все диагностические сообщения сохранены. Обработка NULL-аргумента и обычный выход не меняются. Флаги восстановления не обнуляются преждевременно; при новом открытии watchdog контекст обнуляется и completion инициализируется существующим кодом.

[Исходная правка, точные слова ARM, сборщик и тест](../experiments/wifi-watchdog-completion/README.md). В предыдущей заметке адрес `0xc096ad9c` ошибочно относился к reset-error: это диагностика NULL-аргумента. Изменённый переход ошибочного завершения находится по `0xc096ad0c`; NULL-путь оставлен прежним.

128 выполнений оригинальных и изменённых инструкций проверили 16 контекстов, обе ошибки, нормальный выход и NULL-аргумент. Проверены completion pointer и идентичные аргументы `vos_trace_msg`, `printk`, `warn_slowpath_null`. Указатель не восстанавливается из R7: уже выставленное событие может обойти его инициализацию. Это не эмуляция планировщика Linux.

## Сборка и установка

Только шесть инструкций изменены в распакованном ядре; неудачный эксперимент PNO сюда не включён. Более сильное XZ-сжатие с прежним словарём 32 MiB и CRC32 позволило сохранить размер и расположение zImage. Проверены распаковка, исходный boot ID convention, неизменные ramdisk и хвост. Новых приложений, служб, опроса или увеличения размера распакованного ядра нет. Дополнительное завершение выполняется только на пути ошибки.

Исходный boot повторно сохранён на ПК и проверен до записи. В TWRP 3.1.0-1 SevenMaxs записан только `/dev/block/mmcblk0p14`, затем проверен полный SHA-256. System, userdata, recovery, radio и EFS не записывались. Windows administrator и fastboot не использовались. Android успешно загрузился; хеш boot проверен повторно.

Установленный образ, 16 MiB: `d2cacd5c413e13a17489b7161062f2e9edbe53c3044c33368380d66df80b8cfc`.

Оригинал для отката: `5d7dd05fd96a1e8041c456ba1ff5018ac98bb0418cf38b521f8e602651316e62`.

## Реальная проверка

Экран временно удерживался включённым при USB, чтобы отдельная проблема фонового поиска не смешивалась с восстановлением службы. Исходное `stay_on_while_plugged_in=0` возвращено после испытания.

| Цикл | Результат |
|---|---|
| 1 | Настоящий `WDI_NV_DOWNLOAD_RESP` timeout, неудачный re-init, выход watchdog. HAL вернулся к ожиданию запросов (`binder_thread_read`); ни один проверенный поток HAL не ждал в `vos_watchdog_close`. В первое окно 70 с интернет не восстановился. Отдельная повторная команда включения вернула подтверждённый интернет за 23,48 с. |
| 2 | Подтверждённый интернет после первого включения за 23,44 с. |
| 3 | Подтверждённый интернет после первого включения за 23,19 с. |

В двух последних циклах драйвер успешно загрузился, без повторного NV-download timeout в сохранённом журнале. Время до подтверждённого интернета включает выбор сети, подключение и Android network validation; это не только время загрузки драйвера.

Во время трёх циклов ядро и system_server не перезапускались. Новых ANR/native crash не обнаружено. Старые сообщения NV timeout и kernel WARN при неудачном восстановлении сохранены, а не скрыты. Этот раунд не объявляется проверкой «без ошибок». До правки аналогичный failed reset оставлял HAL в `vos_watchdog_close` и требовал перезапуска. Подтверждено устранение этого зависания в наблюдённом сценарии, а не всех ошибок Prima.

## Состояние и ограничения

Правка оставлена установленной по запросу владельца. Wi-Fi подключён с подтверждённым интернетом; Location включена, Bluetooth выключен, rooted debugging сохранён. Сверка прежнего system repair bundle показывает 0 изменений: датчики, Bluetooth HFP, GPS и Google configurator не затронуты. Временные recovery-образы исчезли из `/tmp` при загрузке; личные журналы и полные образы находятся только на ПК.

Длительный сон, расход батареи и работа несколько дней с этим ядром ещё не проверены. Android 13 и другие ядра не поддерживаются. Комплект system-ремонтов по-прежнему не содержит boot: этот образ и его откат отдельны. Для отката через TWRP нужно вернуть сохранённый оригинал boot и проверить SHA-256, не трогая userdata/EFS/radio.

Следующие задачи — причина NV-download timeout и отдельный сценарий поиска сохранённой сети при выключенном экране. Автоматический бесконечный повтор включения не добавлен и как ремонт не предлагается.
