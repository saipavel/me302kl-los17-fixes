# Сон планшета: исправлена маска диагностических логов датчиков

11 ноября 2026 исследование Wi-Fi при сне выявило другую проблему: диагностические сообщения DSP датчиков регулярно будили планшет. Установлен и проверен второй вариант callback в `/vendor/bin/sensors.qcom`. Данные датчиков, Significant Motion и автоповорот не отключались.

## Что показала проверка Wi-Fi

После подключения к рабочей сети прошли обмен с внешним IP и проверка разрешения имени. Соединение сохранялось в коротком screen-off тесте с USB; после обоих тестов без USB оно было установлено и обмен снова прошёл с 0% потерь (три ICMP-пакета к внешнему IP, один к разрешённому по DNS имени). Это короткие проверки, не оценка качества сети за весь период сна.

В kernel ring во время этих проверок не было `Failure in host offload REQ WDI API`. Ранее такие сообщения сопровождались запросами к отсутствующей ассоциации/нулевому BSSID. Функциональный дефект Wi-Fi в этих условиях не воспроизведён; Wi-Fi-драйвер и настройки энергосбережения Wi-Fi не менялись.

После перезагрузок сеть подключалась владельцем вручную. Автоматическое подключение после загрузки отдельно не доказано; отсутствие соединения до ручного выбора ещё не устанавливает его причину.

## Обнаруженная проблема датчиков

В первом тесте все 27 записанных причин возобновления сна указывали на IRQ 170 (`smd_dev`); активным источником был `smd_sns_dsps`. За интервал снимков `sns_async_ev_wakelock` удерживался ещё около 280 секунд. Активным клиентом Android в конце теста был Significant Motion от Google Play services, но этого недостаточно, чтобы обвинять приложение: диагностический трафик оказался отдельным потоком.

В ограниченной восьмисекундной трассировке `sensors.qcom` получено 79 пакетов: SMR service 7, message 3, log type 62. По определениям `sns_smr_header_s` и `SNS_DEBUG_LOG_IND_V01` это **диагностические логи**, а не обычные показания акселерометра.

Первый ремонт 10 ноября ограничил ошибочный цикл таблицей из 52 ID и восстановил отправку маски. Но маска начиналась с нуля: она правильно выставляла биты для известных типов 0–51, оставляя биты 52–63 нулевыми. В этом протоколе **1 означает запрет лога**, 0 — разрешение. Поэтому неизвестный хосту тип 62 оставался разрешённым. Старый ASUS callback тоже строил только свою известную часть маски; перенос этой логики не учёл несовпадение поддерживаемых типов у текущего DSP и старого host-daemon.

Исправление: перед ограниченным обходом и сдвигами 64-битная маска заполняется единицами. Для 52 известных типов продолжают использоваться настоящие ответы DIAG `log_status`; остальные 12 типов остаются запрещены по умолчанию. Это исправляет обработку диагностической маски, сохраняя обычные запросы и события датчиков.

## Измерения до и после

| Показатель | Первый callback | Исправленная полная маска |
|---|---:|---:|
| Интервал между снимками, с | 355.64 | 420.46 |
| Оценка времени в системном suspend, с | 33.76 | 333.25 |
| Добавленное время `sns_async_ev_wakelock`, с | 280.067 | 3.138 |
| Возобновления с IRQ 170 / sensor DSP | 27 | 0 |
| Счётчик успешных suspend | +27 | +28 |
| Неуспешные попытки suspend | +5 | +2 |
| Связь после возврата | COMPLETED, ping/DNS прошли | COMPLETED, ping/DNS прошли |

Интервалы разной длины, включают подготовку и USB-подключение; это **не** точный трёхминутный лабораторный тест и не измерение времени работы батареи. Оценка suspend получена по разнице приращений boot-based `/proc/uptime` и monotonic времени `/proc/timer_list`. USB удерживает отдельный wake source и потому отключался владельцем. Остаточные краткие отмены freeze сами по себе не доказывают неисправность.

После исправления наблюдались пробуждения Wi-Fi и GPIO/MPM; сенсорных IRQ среди причин возобновления не было. Это не обещает отсутствие любых будущих wake-up или конкретный процент экономии батареи.

На планшете наблюдались отправка новой маски `0xffffffffffffffff` и ответ DSP. В новой трассировке тип 62 отсутствовал; обычные SMGR-сообщения продолжали приходить. После теста отдельно проверены свежие, увеличивающиеся timestamps акселерометра при временном включении штатного слушателя ориентации. Настройка автоповорота возвращена в исходное значение 0. Новых записей crash buffer не было, PID датчиков оставался тем же после загрузки. Хеши Bluetooth, NMEA/HIDL и GPS power adapter не изменились.

## Бинарная воспроизводимость и откат

- ROM: `lineage-17.1-20230306-UNOFFICIAL-duma`, ARM32.
- Файл: `/vendor/bin/sensors.qcom`, 220508 байт, `root:shell`, `0755`, `u:object_r:sensors_exec:s0`.
- Исходный непочиненный файл: `9c0382d044af946ce755feaa7938e1a48c6773edc2ef8a6396a6443634b55f9b`.
- Первый ремонт: `92c61ca6d25e155e6da045195ea76292d4e2eb78c07c5db5ba9b8ceaa50d13cc`.
- Новый установленный файл: `6bb266619a744ca166f1e71e39897fb0205a4ddaecb993034f96711ce9228607`.

Меняется только прежний слот `0x11760..0x117db`: новый код занимает все 124 байта. Размер файла, ELF-сегменты и unwind-запись сохранены. Из-за двух добавленных байтов скорректирован PC-relative литерал указателя таймера. **316 проверок ARM-эмуляции** прошли для новой маски: каждый известный бит, случайные статусы, ASLR, границы таблицы, сохранение регистров/стека, ошибки allocation/header/send и освобождение таймера.

Публичные материалы: [собственный ARM callback](../tools/sensor-logmask-v2/callback.S), [проверяемые дельты](../patches/2026-11-11.json), [краткие результаты без личных данных](../evidence/sensor-sleep-2026-11-11.json). Полные firmware-файлы, сырые трассы и имена Wi-Fi-сетей не публикуются.

Из корня репозитория:

```text
python tools/patch_rom.py --manifest patches/2026-11-11.json sensors-logmask-v2 sensors.qcom.v1 sensors.qcom.v2
python tools/patch_rom.py --manifest patches/2026-11-11.json --reverse sensors-logmask-v2 sensors.qcom.v2 sensors.qcom.v1-restored
```

Для исходного непочиненного файла вместо `sensors-logmask-v2` используется `sensors-v2-from-original`. Оба пути проверены вперёд и назад побайтово; изменённый вход отвергается. Генератор не устанавливает файлы на планшет и не перезаписывает существующий результат. Манифест 10 ноября сохранён для исторических ремонтов.

Нельзя записывать новый файл через `cat` поверх выполняющегося daemon: Android отвергает это как `Text file busy`. Установка выполнена через отдельный проверенный файл, сохранение прав/SELinux-контекста и атомарную замену, затем полную перезагрузку. После перезагрузки раздел system подтверждён в режиме чтения. Для отката подготовить проверенный v1 или оригинал, применить тот же безопасный способ и перезагрузить полностью. Возврат к v1 возвращает ограничение маски; к оригиналу — прежнее падение daemon.
