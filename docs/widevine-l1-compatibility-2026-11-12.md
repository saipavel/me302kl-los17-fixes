# Widevine L1: старый OEMCrypto несовместим с установленным CENC

12 ноября 2026. Локальный аудит официальной ASUS ROM и работающего планшета. Системные библиотеки не заменялись, OEMCrypto/keybox test utilities не запускались.

## Найденная реализация

Официальный `libwvdrm_L1.so` — верхний старый компонент, зависящий от `libWVStreamControlAPI_L1.so` и STLport. Низкоуровневый защищённый интерфейс найден в `system/vendor/lib/libdrmdecrypt.so`, а не в отдельном `liboemcrypto.so`. Он экспортирует `_oec01`–`_oec14`, дополнительные функции ION и keybox и импортирует QSEECom.

На работающем планшете уже есть другая версия `libdrmdecrypt.so`, которая предоставляет то же старое семейство символов. Следовательно, наличие этой библиотеки само по себе не устраняет fallback современного CDM на L3.

Имена `_oec01`–`_oec14` соответствуют старому интерфейсу Initialize/Terminate, entitlement key/control word, decrypt video/audio и secure playback. Их публичное описание доступно в [старом AOSP OEMCrypto.h](https://android.googlesource.com/platform/hardware/ti/omap4-aah/+/master/security/tf_sdk/include/OEMCrypto.h). Совпадение имён не подтверждает полную совместимость конкретных реализаций или протокола TrustZone.

## Почему подмена имени не исправляет L1

Установленный `libwvdrmengine.so` ищет `liboemcrypto.so`, содержит проверку версии и семейство `_oecc…` lookup strings/wrappers. Его код/журналы относятся к session-based CENC, derived keys, RSA provisioning, LoadKeys/SelectKey и другим операциям. Это не тот же набор функций, что старые `_oec…` entitlement/control-word операции. Современный публичный пример session-based интерфейса: [Chromium OEMCrypto service](https://chromium.googlesource.com/chromium/src/+/a47894aed272181d31390d7a4106e47d1ffd8a55/components/arc/mojom/oemcrypto.mojom).

Символы и хеши сопоставлены в [evidence](../evidence/widevine-l1-compatibility-2026-11-12.json). Не все найденные строки обязательно являются обязательными вызовами для каждой конфигурации CDM; точный минимальный набор и версия API не установлены. Однако оснований считать ABI взаимозаменяемым нет. Простое переименование библиотеки или экспортирование другого имени для старой функции не реализует отсутствующие криптографические операции и доверенный протокол.

## Защищённое приложение

В официальном `libdrmdecrypt.so` есть обращения QSEECom к приложению `widevine`, пути `/system/etc/firmware` и `/firmware/image`, проверка `widevine.mdt`. Поиск файлов с widevine/oemcrypto в доступных live firmware directories ничего не вернул; таких отдельных файлов нет и в извлечённом официальном system firmware directory. Это **не доказывает**, что приложение отсутствует во всех разделах или не может загружаться иным способом: содержимое защищённой среды и альтернативные контейнеры на этом этапе не исследовались.

Для настоящего L1 нужен согласованный CENC CDM/OEMCrypto/доверенное приложение с поддержкой этой аппаратной платформы и её штатного provisioning. Получить это только адаптацией старых имён функций пока не представляется обоснованным. Нет найденного совместимого комплекта, который можно безопасно проверить подменой одной библиотеки. Сторонние keybox, подмена уровня безопасности и изменение TrustZone не проводились.

## Практический результат

Аппаратный secure AVC отдельно прошёл lifecycle с экспериментальными repairs, а программный Widevine L3 уже прошёл получение лицензии, расшифрование и rendering. Между ними пока отсутствует совместимая аппаратная DRM-реализация. Постоянно включать экспериментальный secure codec на основании этих результатов рано. Этот аудит не дал новой устанавливаемой правки L1; рабочая L3-конфигурация сохранена.
